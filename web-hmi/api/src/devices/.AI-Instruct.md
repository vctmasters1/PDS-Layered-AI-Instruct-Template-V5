# .AI-Instruct.md (Devices Handler Registry)

> **Parent**: `devices-hmi/.AI-Instruct.md`

> **URL Context:** The devices section is served at `pipedreamsystems.com/devices`. This is a path-based route under the same domain as the marketplace (`/marketplace`). Shared origin means JWT auth and cookies work seamlessly across both sections. Do **not** reference `devices.pipedreamsystems.com` (deprecated subdomain) anywhere in this module.

This directory contains the **device management module** — a plugin-based system for browser-based provisioning, configuration, firmware management, and real-time interaction with PipeDream embedded devices.

## Platform Assumptions

- **Web-first**: All user interaction is via a web application served over **HTTPS** (TLS 1.2+)
- Designed for future wrapping in a native app shell (PWA, Capacitor) if needed

## Communication Paths

| Path | Protocol | Purpose |
|---|---|---|
| Browser ↔ Server | **HTTPS** | Save/load configs, user auth, firmware metadata, device registry |
| Browser/Phone ↔ Device | **BLE** (Web Bluetooth API) | Direct local config writes, provisioning, Wi-Fi setup, firmware OTA |

- The browser connects **directly to the physical device via BLE** for real-time provisioning, configuration, and firmware updates
- The server stores configs, firmware binaries, user data, and device registry — the device does not need to reach the server
- BLE packet definitions (encode/decode) are a **frontend** concern since the browser is the BLE central
- All browser↔server communication uses industry-standard security: HTTPS, JWT/session auth, input validation, rate limiting

## Architecture

```
devices/
  index.ts                ← Device handler registry (maps type slug → handler)
  types.ts                ← Shared interfaces (IDeviceHandler, IConfigSchema, IPacketDefinition)
  _template/              ← Reference template — copy to create a new device handler
    index.ts              ← Handler scaffold with TODO placeholders
    config-schema.ts      ← Example config parameters
    firmware-versions.ts  ← Firmware version list scaffold
    routines.ts           ← Optional protocol routines scaffold
  generic/                ← Generic fallback handler (active — used by all types with no specific handler)
  aero-ctrl/              ← Aeroponic Controller handler (registered)
  h20-chiller/            ← H2O Chiller handler (registered)
  portioning-feeder/      ← Portioning Feeder handler (kept, not currently registered)
  <device-type>/          ← One directory per device type (plugin pattern)
    index.ts              ← Exports handler, metadata, display name
    config-schema.ts      ← Adjustable parameters for this device (version-aware)
    firmware-versions.ts  ← In-code firmware version list (newest first)
    routines.ts           ← Provisioning, OTA, protocol-specific logic (optional)
```

## Adding a New Device Type — Checklist

> **Use `_template/` as a starting point.** Copy the entire directory, then follow each step.

- [ ] **1. Copy template** — `Copy-Item -Recurse _template/ <device-type>/` (kebab-case slug)
- [ ] **2. Set identity** — In `index.ts`: replace `TODO_DEVICE_TYPE` with slug, `TODO_DISPLAY_NAME` with human name
- [ ] **3. Set protocols** — In `index.ts`: update `protocols` array (`CommProtocol.HTTP`, `.BLUETOOTH`, `.WEBSOCKET`, `.MQTT`)
- [ ] **4. Define config params** — In `config-schema.ts`: replace example params with real adjustable parameters
- [ ] **5. Version the schema** — Add entries to the `configSchemas` Map keyed by firmware version (newest first)
- [ ] **6. List firmware versions** — In `firmware-versions.ts`: add real firmware versions with changelog, binary size, SHA-256
- [ ] **7. Implement routines** *(if needed)* — In `routines.ts`: define `IPacketDefinition` structures for BLE/binary protocols, implement `encodeConfigPacket` / `decodeConfigPacket` in `index.ts`
- [ ] **8. Create .AI-Instruct.md** — Describe the device's purpose, what it controls, communication protocols, parameter table, firmware status, and TODO implementation gaps
- [ ] **9. Register handler** — In `devices/index.ts`: import and call `registerDevice(handler)`
- [ ] **10. Verify** — Start dev server, call `GET /api/devices/types`, confirm the new device appears

## Key Design Decisions

- **Config schemas are firmware-version-aware** — `getConfigSchema(firmwareVersion)` returns the parameters appropriate for the device's current firmware. Different firmware versions may expose different parameters.
- **Binary protocol support available** — Device handlers define `IPacketDefinition` structures for BLE characteristic encode/decode. These definitions are used by the frontend (Web Bluetooth API) to communicate directly with the physical device. The server stores configurations as JSON; the frontend translates to/from BLE packets.
- **Config history is immutable** — Every config change creates a new `DeviceConfig` row. The `Device` entity tracks `currentConfig` (acknowledged) and `pendingConfig` (not yet confirmed).
- **Firmware binaries stored externally** — The `Firmware` entity stores metadata (version, SHA-256, size, path). Actual binaries live on the filesystem or object storage.

## QR Code Flow

1. QR on device encodes: `https://pipedreamsystems.com/devices/<type>/<serial>`
2. Frontend loads config schema from registry → renders parameter form
3. User adjusts parameters → POST to `/api/devices/<serial>/config`
4. Browser connects to device via BLE (Web Bluetooth API) and writes the config directly

## Conventions

- Device-type slugs are **kebab-case** (e.g. `silabs-widget`, `led-controller`)
- All firmware versions use **semver** (e.g. `1.2.3`)
- Config payloads are always JSON at the API layer, even if the device uses binary protocols internally
- Use `CommProtocol` enum from `types.ts` to declare supported protocols
